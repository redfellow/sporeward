# Design

## Context

See [proposal.md](proposal.md) for motivation. `previewEncounters` and `useEncounters` already derive outbreak contacts and persist earliest per-outbreak observations in `contact_previews`. The saved shape is only target ID, contact time and estimated points; it has no name, reason or lab records. `RouteMap` independently derives provisional lab contacts with shared `matchContacts`. `CleanupFeedback` announces received world clearances and does not establish personal contribution. `App.tsx` owns the active outing, loads saved fixes on foreground return and keeps recording state across map/help navigation.

Extend the existing [outing-feedback contract](../../specs/outing-feedback/spec.md). Preserve [contact matching](../../specs/gps-contact-matching/spec.md) and [recording recovery](../../specs/native-recording-recovery/spec.md), rather than creating another scorer or location pipeline. Destination focus and Nearby are implemented in open PRs [#25](https://github.com/redfellow/sporeward/pull/25) and [#26](https://github.com/redfellow/sporeward/pull/26), respectively; both still have separate phone acceptance.

## Goals / Non-Goals

**Goals:** Explain known personal contacts at the time they happen, retain them for screen-off review, and make feedback safe across navigation, recovery and refresh.

**Non-Goals:** Background notifications, sounds, haptics, new GPS sampling, new contact eligibility, scoring changes, a second activity total, a world event feed or a new historical outing screen. Finished outings continue through the existing authoritative recap.

## Decisions

- **Own feedback above the map.** Add an app-owned contact-feedback hook/controller keyed to recording owner, server/world identity and active outing, separate from whichever outing history displays. Feed it existing outbreak observations, shared-matcher lab contacts, the current offer and any matching receipt. Keep UI selection in the map; navigating to help/history must not recreate announcement identity. Do not mount active feedback in recap maps.
- **Use a pure reducer and formatter.** Normalize evidence into one entry per target kind/ID per outing/world, with original contact time, a saved display name/type and captured local estimate/reason when known. Retain earliest contact evidence; subsequent snapshots do not reprice the original estimate or create another event. This is a presentation summary, not a restriction on server-eligible repeat visits. Derive held-versus-provisional wording from existing eligible-distance progress. Show no-estimate generically when evidence cannot distinguish cooldown or another cause. Matching authoritative results override the displayed outcome without adding a new contact or changing global totals.
- **Add a small local feedback table.** Store scalar contact summaries plus an announcement-consumed flag, indexed by outing/context and target kind/ID. Use the existing serialized SQLite writer and idempotent upserts; do not write on every fix, duplicate geometry or modify existing preview/scoring rows. Check outing ownership on reads/writes. Store Field Lab observation metadata here so later expiry/removal cannot erase a known contact. The log is newest first with stable target keys and original recorded times. A log entry is never uploaded as authoritative evidence.
- **Hydrate quietly.** On initialization and foreground return, load persisted feedback before deciding whether evidence is new. Existing previews and saved fixes can populate the log silently. Distinguish live ingestion from restore/catch-up and delayed-world reconstruction using foreground/map visibility, recording state and the fix-processing watermark; a newly discovered old contact is not a live event. Old zero-point previews have unknown reason, so do not invent cooldown history. If old evidence cannot be attributed to the current world, do not recast it as a new-world contact. With neither usable world nor recorded contact evidence, show contact information unavailable; ordinary upload/recap can still settle the outing.
- **Consume once before displaying.** Persist each entry's announcement decision before emitting a live notice. Catch-up, hidden and restored entries are marked handled silently; remounts and authoritative updates never requeue them. After a crash between persistence and display the banner can be missed, but the log remains available. Prefer that at-most-once behavior over a replayed reward celebration. A persistence error must not stop recording or invent confirmed feedback; explain unavailable log persistence and leave normal recorder recovery intact.
- **Bound visual feedback.** Proposed UI tuning: group contacts arriving within roughly one second, show one brief banner for about four seconds, and keep at most one pending aggregate instead of a growing queue. Preserve individual entries in the log. Start with text/type cues and restrained game colors; example copy is `Outbreak reached · ~70 visit points awaiting validation`, `Contact recorded · points held until outing qualifies`, or `Field Lab reached · collection pending upload`. Numeric estimates use observed values, never hardcoded rewards. Confirmation remains an upload/recap concern.
- **Share map space deliberately.** Add a Recent contacts control for active or paused outings and a bounded virtualized sheet above the recording HUD. Coordinate it with Nearby, destination cards and cleanup feedback so only one competing surface occupies the notice area. Suppress notices while another surface is open, keeping their entries in the log without a later banner burst. Close/Android Back dismisses the log first and preserves the map/pin. Any world-clearance notice stays impersonal; it must not imply the player's contact caused the clearance.
- **Keep cost and state boundaries narrow.** React only to new evidence, activity/identity/lifecycle changes or received authoritative outcomes; never camera animation frames. Reuse the recorder's existing two-second foreground refresh and foreground-return load. No extra GPS watch, polling loop, native background work or server endpoint. Local storage is additive, and native geography/artwork remain inside the accepted MapLibre pipeline.

## Risks / Trade-offs

- [Estimated points sound earned] → Explicit awaiting-validation/held language, no invented reasons, no cleanup award claims, and receipt outcomes replace provisional display.
- [Screen-off contacts disappear before the map reloads] → Retain already known metadata and reconstruct from available saved evidence silently. A contact lacking both usable matching context and prior evidence cannot be invented; final recap remains authoritative.
- [Initial hydration or delayed world loading looks like a fresh ride] → Test explicit restore/catch-up/live transitions, including out-of-order persistence, before emitting banners.
- [Feedback writes contend with recording] → Existing writer queue, small idempotent batches only for new/changed entries, no geometry or full GPS copies.
- [Logs or notices follow the wrong account/world] → Context-keyed storage, owner checks and cancellation/generation guards around asynchronous loads and writes.
- [More HUD hides useful map controls] → Bounded mutually exclusive surfaces; retain pause/finish and owner narrow/wide phone acceptance as a separate gate.

## Migration Plan

Add the local table idempotently without rewriting recordings, IDs, segments, contact previews, upload receipts or field-world data. Hydrate legacy current-outing observations silently with generic unknown metadata where attribution is sound; do not bulk backfill completed outings or guess missing world identity. Add focused SQLite upsert/reopen tests and pure lifecycle tests using synthetic evidence. Rollback disables feedback UI/ingestion and leaves the additive table and original recorder data intact. No service deployment or authoritative migration is needed.

## Local persistence implementation

`contact_feedback` is additive and keyed by owner, activity, server environment, world start and target kind/ID. Scalar JSON bodies hold earliest evidence, optional authoritative outcome and consumed status. Reads check the activity owner; writes run through the recorder's existing serialized exclusive transaction. Only changed entries are written and consumed claims are returned after commit. The table is not part of uploads. Disabling the feedback hook/UI rolls back the feature while leaving saved recording tables and the unused metadata table intact.

Focused real SQLite tests passed for duplicate claims, reopen, authoritative update, owner/world/environment isolation and preservation of existing fix, preview and receipt rows. These are isolated local database tests, not native-device evidence.
