# Prospective resistance scoring

Resistance is opt-in: `WorldStore.configureResistance(true)` records an activation timestamp, starts all accounts neutral, and preserves the existing world snapshot. `RESISTANCE_SCORING=enabled` invokes this at server startup; `disabled` switches back to legacy scoring while retaining personal events and confirmed awards. An absent variable leaves stored configuration untouched. A fresh world has no resistance configuration. No deployment is part of this change.

Accepted ordinary contacts recorded at or after activation use scoring version 2 and the [calibrated rules](resistance-calibration.md). Contacts recorded before activation use legacy rules even when uploaded later. Awards and recaps persist their scoring version and confirmed points; later events never recalculate them. Cleaning strength, treatment delivery, lifetime extension, cooldowns, remnants and cleanup/protection awards retain their existing mechanics. Protection awards remain full value.

Personal resistance and fixed outbreak representative points live in the same versioned snapshot and transaction as contributions and awards. PostgreSQL's existing world advisory lock and snapshot row lock serialize server instances; the file adapter supports a single WorldStore instance per directory. It does not provide multi-process file locking. The account session chooses the private state; callers cannot choose another player through query input. `/world` returns only that owner's centre, circular radius, centre resistance and rules/activation versions, alongside ordinary visit offers. Contribution locations and history are not returned. Runtime parsers reject malformed private fields and unsupported scoring versions. `/activities/:id/encounters` retains existing owner-scoped access and returns stored awards.

Late contributions are priced against known events preceding contact time. Newly accepted events enter present resistance with their recorded timestamps and passive decay. Late evidence does not rewrite already confirmed awards, so different upload orders can produce different earlier awards. Cleaning strength is the strength actually committed by the existing engine, including its known history at settlement; no historical strength is retroactively recomputed. Overlapping source evidence can refine the legacy contact time, but its already committed resistance event retains its original timestamp and identity. Retries and scheduled treatment delivery cannot add another event.

Account separation, concurrent retries, restart, both late delivery orders, neutral activation, owner-only map/recap access and map-to-award agreement run in `npx vitest run apps/server/src/resistance-state.test.ts`. These file-backed checks do not claim live PostGIS or Android validation.

## Migration and rollback

Run `node --import tsx scripts/world/check-resistance-migration.mts`. This creates synthetic legacy snapshots and a recording under a fresh temporary directory, verifies neutral activation, exact preservation of legacy geometry/contributions/cleanup awards/recaps/scores and recording bytes, disables and re-enables scoring, then removes only that temporary directory. It accepts no field paths or credentials.

The migration is an additive optional snapshot member; PostgreSQL persists it inside its existing atomic world transaction. There are no destructive table changes or backfills. Before any separately authorized deployment, back up the database and activity storage through the existing operational procedure. Enable the flag on isolated replay first. To roll back scoring, restart the same build with `RESISTANCE_SCORING=disabled`; new ordinary awards use legacy rules, confirmed version-2 awards stay fixed, and personal events remain retained. Re-enabling keeps the original activation and personal state, rather than granting another neutral reset. Do not strip the optional state or restore a pre-activation backup over newer confirmed awards. Rolling back the binary itself requires a version that preserves this optional state; scoring disablement is the supported reversible path. Live PostgreSQL migration/rollback remains to be exercised in integrated isolated persistence validation.
